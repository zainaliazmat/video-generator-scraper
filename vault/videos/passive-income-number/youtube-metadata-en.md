### ⚠️ A `check` failure worth writing down: `sweep_static` on a one-clip project

The first build carried the `japanese-money-methods` timeline pattern verbatim — a proxy tween, `.to({ t: 0 }, { t: 1, duration: 4 })` — and `check` failed:

```
Layout ✗ t=0s sweep_static [data-composition-id] — Timeline did not advance under seek;
every green verdict on this run is unreliable.
```

The recorded lesson from that project is *bisect the diff before believing the error message*, because there the identical message was caused by an overflowing `nowrap` line and the fixHint pointed at the timeline. So the copy was bisected first: `.type` max-width is 660 px and the widest line measures 608 px — **no overflow**. The tween was not the cause either.

**The cause is structural, and it is new: it is a consequence of the one-thumbnail rule.** That project held TWO 2-second clips inside a 4-second composition, so seeking swapped which section was visible and the sweep saw different pixels — the proxy tween never had to do any work. This project ships ONE thumbnail (creator rule 2026-07-29), so a single clip spans the whole composition and every seek returned an identical frame. **The checker was telling the truth.** Fixed by giving the *photograph* a real 4-second drift (`fromTo("#plate-en", {scale:1}, {scale:1.04})`), scoped so the type never moves, and exporting at **`--at 0`** where the plate scale is exactly 1.000 and the documented crop arithmetic holds byte-for-byte. The 8 cosmetic `container_overflow` infos the drift produced are declared with `data-layout-allow-overflow` rather than silenced.

**Every future one-thumbnail project in this repo will hit this.** It is not a per-video quirk.
